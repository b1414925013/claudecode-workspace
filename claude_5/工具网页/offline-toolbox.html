Base64 是什么？原理是什么？
把任意字节流按 3 字节（24 bit）一组重新切成 4 份、每份 6 bit，再映射到 A–Z a–z 0–9 + / 共 64 个可打印字符。体积约增大 1/3。它是编码而非加密，任何人都能还原。
末尾的 = 是什么？可以去掉吗？
字节数不是 3 的倍数时，用 = 补齐到 4 的倍数，最多两个。URL、JWT 等场景常把填充去掉，解码时按长度自动补回即可——本工具解码已自动容忍缺失填充。
标准 Base64 与 URL-safe 的区别？
+ 和 / 在 URL / 文件名中有特殊含义，需替换为 - 和 _（RFC 4648 §5）。JWT 的头和载荷就是「URL-safe + 去填充」。本工具勾选「URL 安全」即可输出该格式，解码时两种会自动兼容。
中文为什么乱码？本工具如何避免？
乱码根因是编码与解码使用了不同字符集（如一边 GBK 一边 UTF-8）。本工具两侧共用同一个字符集选择：选 GBK 编码出的 Base64，用 GBK 解码即可还原；用 UTF-8 去解才会乱。
为什么浏览器 btoa 处理中文会报错/乱码？
btoa() 只接受 Latin1 范围字符。正确做法是先用 TextEncoder 把字符串转成 UTF-8 字节再编码（见「代码示例」页）。本工具内部就是这么做的。
自动模式是如何判断方向的？
依次检查：① 有 data:…;base64, 或 base64: 前缀 → 解码；② 含 Base64 字母表之外的字符 → 编码；③ 长度 < 8 的短文本 → 编码；④ 其余先尝试解码，若结果可读（乱码率 ≤ 10%）则解码，否则回退为编码。想强制方向请切换到「编码 / 解码」。
GB18030 编码方向有什么限制？
浏览器原生只提供「解码」能力，本工具通过反向映射表补齐了「编码」方向：GB18030 覆盖常用两字节汉字区；生僻字与 emoji 请改用 UTF-8，工具遇到无法表示的字符会明确报错而不是悄悄替换。
大文件会卡吗？数据安全吗？
文件转换采用分块处理，建议 ≤ 100 MB。所有计算都在你的浏览器内完成，零网络请求，本页面保存后断网也能用。
